# LyCAD

基于 **C++20 + Qt6 + CMake** 的二维 CAD 绘图软件。功能定位对标 AutoCAD 的基础绘图与编辑能力，
支持 **DXF / DWG** 图形文件的导入导出，代码按「文件解析 / 几何模型 / 渲染显示 / 用户交互」等职责清晰分层。

---

## 1. 快速开始

```bash
# 依赖：CMake ≥ 3.21、支持 C++20 的编译器、Qt 6.5+ (Core/Gui/Widgets/Svg/PrintSupport)
#       Debian/Ubuntu 上 Qt 开发包为 qt6-base-dev qt6-svg-dev
#       libdxfrw-modify（DWG/DXF 原生解析，libdxfrw 修改版）已随仓库内置，
#       不需要单独安装；它依赖 iconv，
#       glibc 自带、无需额外安装，macOS 等平台由 CMake 自动链接
cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release
cmake --build build -j              # 默认只编译主程序

./build/lycad                       # 启动
./build/lycad drawing.dxf           # 启动并打开文件

# 测试与开发工具按需构建（ctest 不会自己编译缺失的二进制）：
cmake --build build --target lycad_tests -j
ctest --test-dir build --output-on-failure   # 运行测试
```

### 构建选项

| 选项 | 默认 | 说明 |
|---|---|---|
| `LYCAD_BUILD_TESTS` | ON | 定义单元测试目标（不在默认构建里，用 `--target lycad_tests` 按需编译） |
| `LYCAD_BUILD_TOOLS` | ON | 定义开发工具目标（同上，用 `--target lycad_tools` 按需编译） |
| `LYCAD_ENABLE_ASAN` | OFF | 启用 AddressSanitizer / UBSan |
| `LYCAD_WARNINGS_AS_ERRORS` | OFF | 将编译告警视为错误 |

## 2. 模块结构

```
CMakeLists.txt    构建脚本（源码清单 + 可执行程序 + 安装规则）
src/
├── core/       几何模型    7,854 行  —— 基础数学、图元、图层/文字样式表、文档、撤销栈
├── io/         文件解析    3,920 行  —— DXF 编解码器、libdxfrw-modify 适配层、DWG 后端、注册表
├── render/     渲染显示    2,606 行  —— 视图变换、图元绘制、画布控件、出图与分页
├── interact/   用户交互    5,946 行  —— 对象捕捉、工具状态机、命令注册表、坐标解析
└── ui/         界面装配    4,688 行  —— 主窗口、功能区、主题、图标库、面板、命令行、打印对话框
third-party/
└── libdxfrw-modify/
              DWG/DXF 原生解析 85,660 行（libdxfrw 修改版，GPL-2.0-or-later，详见第 8 节）
              目录内只保留参与编译的源码（src/）与 COPYING、AUTHORS
resources/        40 枚 SVG 图标 + 资源清单
tests/          3,680 行（自带 CMakeLists.txt）
tools/          1,827 行（自带 CMakeLists.txt）
```

**本项目自己写的**构建描述只有三处：根 `CMakeLists.txt`、`tools/CMakeLists.txt`、
`tests/CMakeLists.txt`；`src/` 与 `resources/` 下只有内容，没有任何构建脚本。

`third-party/libdxfrw-modify/` 是 **libdxfrw 0.6.3 的永久修改版**：不再跟随上游，
因此目录按「只保留编译所需」裁剪——上游的构建脚手架（autotools 一套与自带的
`CMakeLists.txt`）、示例程序（`dwg2dxf/`、`dwg2text/`、`bin/`）、自带测试、Docker 与
VS 工程、文档全部不随仓库分发，由根构建脚本把它的源码统一编入。目录里只有
`src/`、`COPYING`（GPL 全文，分发时必须随附）与 `AUTHORS`（署名）。
对上游源码的修改清单见第 8 节。

`third-party/libdxfrw-modify` 是唯一随仓库分发的第三方源码：它编成一个**独立目标**
（对象库，不产出 `.a`），因为第三方代码不能套用本项目的 `-Wall -Wextra`
（它有自己的书写风格，上百条告警会把真正的问题淹没），而 CMake 的「源文件属性」
只在同一目录内可见，`tools/` 与 `tests/` 下的目标读不到在根目录设的属性。

**依赖方向严格单向，无循环：**

```
ui ──> interact ──> render ──> core
          │            │         ^
          └──> io ─────┴─────────┘
```

模块不再编译成独立的库，构建过程里也没有任何 `.a` / `.so` 中间产物：五个模块的源文件用
**一段 `file(GLOB_RECURSE)`** 一次收齐，直接编进各个可执行文件。模块划分体现在目录上，
新增 `.h` / `.cpp` 放进对应目录即可，不必改构建脚本。

glob 带 `CONFIGURE_DEPENDS`——裸的 glob 只在配置阶段展开一次，之后新增的文件不会被编译，
**而且不报错**，这类遗漏往往只在别人机器上才暴露。带上它之后，构建系统每次构建都会检查
目录内容，有变化就自动重新配置（代价是每次多一次目录扫描，这个规模可以忽略）。

不需要完整功能的可执行文件，从同一份清单里**过滤**出子集：

| 可执行文件 | 编入的源码 |
|---|---|
| `lycad` / `lycad_icon_sheet` / `lycad_ui_snapshot` | 全部五层 |
| 4 个单元测试 | core + io + render + interact（不含 ui） |
| `lycad_sample_generator` | **core + io** |

最后一行是刻意的：`tools/lycad_sample_generator` 只编入最底下两层，因此一旦 core / io 反向依赖了
渲染或界面层，它会立刻因符号缺失而链接失败——每次构建都做一次依赖方向的契约检查。

代价要说清楚：同一个源文件会被每个用到它的可执行文件各编译一次。实测从零构建约 112 秒
（16 核），若改成五个模块各编一次、多个目标共用对象文件，约 34 秒。换来的是构建脚本里
没有目标图、没有对象文件的传递规则，一眼能看明白。哪天编译时间成了瓶颈，把源码清单改回
对象库即可，其余部分不用动。

### 各模块职责与关键设计

**core —— 几何模型**

| 文件 | 职责 |
|---|---|
| `Types` | `Point2D` / `Vector2D` / `Box2D` / `Transform2D`（2×3 仿射变换）与线段求交等几何算法 |
| `Entity` | 图元抽象基类：标识、图层归属、颜色/线宽的随层解析、包围盒、拾取距离、夹点 |
| `PointEntity` `LineEntity` `CircleEntity` `ArcEntity` `PolylineEntity` `TextEntity` `HatchEntity` `DimensionEntity` `SplineEntity` `EllipseEntity` `InfiniteLineEntity` `InsertEntity` | 十三类图元（含构造线/射线与块参照） |
| `Block` | 块定义（`BlockDefinition`）与块表（`BlockTable`），含属性定义 ATTDEF |
| `Layer` / `Linetype` / `AciPalette` | 图层表、标准线型、AutoCAD 颜色索引 |
| `Selection` | 选择集 |
| `Document` | 图元容器 + 图层表 + 块表 + 文字样式表 + 选择集 + 撤销栈 |
| `Commands` | `QUndoCommand` 实现 |

设计要点：

- **`Document` 刻意不依赖 `io`**，因此不提供 `load/save`。文件读写由 `io::CadFile` 门面完成，
  它通过 `beginBatchLoad()` / `addEntity()` 装配文档。这让 core 处于依赖链最底层，可脱离文件格式独立测试。
- **撤销采用「前置快照」而非「施加逆变换」**。逆变换在非等比缩放下不可逆（圆会被近似为圆，无法还原原半径），
  而快照对任何变换都精确可逆。代价是一次深拷贝，换取的是撤销的绝对正确。
- **圆弧以「逆时针参数化」统一表达**（起始角 → 终止角，跨度 ∈ (0, 2π]），与 DXF 一致。
  镜像是唯一会反转绕行方向的变换，`ArcEntity::transform()` 与 `PolylineEntity::transform()` 对此有专门处理。
- **多段线支持凸度（bulge）**，即含圆弧段的多段线。凸度的符号决定绕行方向，
  因此包围盒、最近点、离散化都必须按符号分支——这是一个容易出错的点，也是测试重点。
- **标注的显示几何不落盘**。`DimensionEntity` 只存定义点，尺寸线/界线/箭头/文字位置
  由 `geometry()` 一处公式实时推导，渲染、DXF 匿名块生成、拾取三处共用同一份结果，
  从结构上杜绝「存下来的图形与定义点不一致」。
- **块参照是「引用」而不是「复制」**。`InsertEntity` 持有块定义的 `shared_ptr`
  （定义在 `BlockTable` 里按名索引，大小写不敏感），几何由
  `T(插入点)·R(旋转)·S(比例)·T(-块基点)` 实时推导，展开结果带缓存供渲染/拾取/捕捉共用。
  导入时**不再炸开** `INSERT`：同一个定义被引用二十次就是二十个引用，文件往返后
  `BLOCKS` 段与 `INSERT` 都还在原处，需要平面化时由 分解(EXPLODE) 显式触发。
  变换的可分解性是这里唯一的坑：块参照的线性部分恒为 `R(θ)·S(sx,sy)`（两列正交），
  左乘任何**相似变换**（平移/旋转/等比缩放/镜像）后两列仍正交，因而总能重新分解回
  `(插入点, 比例, 旋转)` 三个参数；只有非等比拉伸（以及 MINSERT 的阵列偏移）会引入
  错切，此时把结果**烘焙**进该块参照私有的一份匿名块定义副本——几何精确，代价是
  这一处不再是引用。`Document::referencedBlocks()` 因此不能只遍历块表：私有副本
  不在表里，只查表会在保存时把这块内容整块丢掉。

**io —— 文件解析**

- `CadCodec`：`ICadCodec` 接口与 `CodecRegistry`。格式以插件形式注册，
  核心与界面只面向接口编程。注册表在按扩展名匹配时**分两轮**：先找可用的编解码器，
  若都不可用则返回「格式已知但能力不足」的那个，以便向用户说明具体原因，
  而不是一句无信息量的「不支持的文件类型 .dwg」。内置的 DXF 与 DWG 都是随程序编入的，
  恒为可用，这一层是为将来可能引入的、需要运行环境配合的格式留的口子。
- `DxfGroup`：组码层。支持 ASCII 与**二进制 DXF** 两种物理形态，并处理 `\U+XXXX` 转义，
  使中文图层名/文字在任意代码页下都能正确往返。曾尝试让 R2000 直接写 UTF-8 并声明
  `$DWGCODEPAGE = UTF-8`，实测不可行——libdxfrw 不按该声明切换解码器，而是沿用默认
  代码页把 UTF-8 字节又解了一遍，中文全成乱码。转义形式只需在读方补偿一处已知偏差，
  是更可靠的选择。
- `LibDxfRwAdapter`：导入时做一次**坐标体检** —— 非有限值、或超出 1e12（任何真实图纸都
  远小于它）的图元一律跳过并计数上报，不静默丢弃。二进制格式里读错一个字节就能造出
  1e100 这种坐标，放进来会把全图范围撑爆，用户看到的又是「打开是空白」（实测某 2007 版
  DWG 有 2 条样条各一个控制点如此）。适配层把 libdxfrw 的数据结构翻译成 LyCAD 实体模型，
  **DXF 与 DWG 的读取都走这里**（`DxfCodec::read` → `readDxfWithLibDxfRw`）。
  libdxfrw-modify 的头文件只在这个 `.cpp` 里出现，不外溢到项目其它部分。
  适配层内含两处**用实测定标出来的**处理，删改前请先读注释：
  文字旋转在 DXF 与 DWG 两条路径下单位不同（度 / 弧度）；以及它会把
  `\U+XXXX` 转义的前导反斜杠解成 `¥`，导致中文退化成可见转义文本。
  读取时把 `INSERT` **建成块参照**：块定义进 `BlockTable`，块参照指过去，两者都不展开。
  「块内 0 层图元继承 INSERT 图层」与「随块（ByBlock）颜色/线型/线宽取块参照的值」
  这两条标准语义在 `InsertEntity::collectInto` 里统一实现，嵌套块在同一次递归中解析
  （深度上限 16 挡自引用）。属性块也已支持：`ATTDEF` 进块定义的属性表，`INSERT`
  后面的 `ATTRIB` 挂到该块参照上，块参照上缺哪条属性就按定义补默认值。
  DWG 路径也一样：`ATTDEF`/`ATTRIB` 在那里是**独立对象**（不跟在 INSERT 后面），
  属性值靠「同一个属主块记录 + 标签命中该块的属性定义」回填——这条字段序全靠
  与同一张图的 DXF 逐字段对照定标，`test_block_insert` 里的 DWG/DXF 对照测试就是
  那把尺子（插入参数、属性值、属性位置、字高、旋转都要求逐位一致）。
  标注的匿名几何块（`*Dnn`）仅作显示用途，读入后**整块丢弃**——几何由定义点重推导。
  这里必须区分「丢弃」与「不属于任何块」：跳过 `*Dnn` 时若只是把当前块指针置空，
  块内的尺寸线/箭头/标注文字会掉进模型空间，一张四个标注的样图会凭空多出二十个图元。
  样条（SPLINE，de Boor 求值按弦高离散化）与椭圆（含椭圆弧）已建模。
  **无界直线**也已建模：构造线（XLINE）与射线（RAY）由公共基类
  `InfiniteLineEntity` 表达——「基点 + 单位方向向量」与 DXF 的 10/11 组码一一对应。
  这类图元没有有限包围盒，因此范围缩放、出图与 `$EXTMIN/$EXTMAX` 都按「无界」排除它们，
  渲染与捕捉则改用「裁到视口 / 光标邻域」的精确线段（见 `InfiniteLineEntity::clippedTo`）。
  未建模的实体（3DFACE/VIEWPORT/IMAGE/MULTILEADER…）按类型汇总
  计数后跳过，**不静默丢弃**；MTEXT 降级为文字导入并明确告知（提示里写「降级」而不是
  「跳过」——内容没丢，只是换了形式）。降级时按 MTEXT 自身的语义重映射：附着点只决定
  参考矩形哪条边贴着插入点，**行在矩形内的横向位置由段落对齐码决定**（`\pxqc;` 居中、
  `\pxqr;` 右对齐…），所以对齐点要按「插入点 + 矩形宽度（41 组码）」换算，否则整块文字
  会偏最多一个矩形宽（实测某图纸的 `JK` 偏了 40 个单位）。**内联字体码**
  （`\fSimSun|b0|i0|c134|p2;`）也一并还原：按字体名建一条文字样式（TrueType 族名 +
  字符集标志，或 `.shx` 文件名），图元挂到该样式上——丢了这个码，导出后整段字会退回
  样式里的字体（实测英文 `KC-DZS05`/`JK` 从宋体变成单线笔画字体）。段落 `\P` 转为换行、
  其余内联格式码（`{\W1;…}`、`\H…` 等）剥除后**按多行渲染**（详见 addMText 注释）。
  **EDA 导出的 DXF 常缺图层颜色**：当 ≥3 个图层命中常见 EDA 命名（Top-Layer/Bottom-Layer/
  Silkscreen/Board-Outline…）且颜色为默认值时，按行业惯例自动配色并在警告中明确告知。
- `writeDxfWithLibDxfRw`（DXF 写出，同一适配层）：目标版本覆盖 `AC1015 (R2000)` 到
  `AC1032 (2018)` 共六档（清单见 `WriteOptions::availableDxfVersions()`），
  **默认 AC1032**——现代 CAD 都能打开，实体集完整，且文本不再受代码页限制。
  **不含 R12 (AC1009)**：R12 缺 HATCH/SPLINE/ELLIPSE/XLINE/RAY，也没有 TrueType 与
  MTEXT，写出时得把这些图元整体降级改写；这条通道已移除，**R12 只读不写**。
  文字/填充/标注按规范写出（`TEXT` / `MTEXT` /
  `HATCH` / `DIMENSION` + 匿名几何块，使不具备标注重绘能力的旧软件也能显示）；
  含换行的多行文字写回为 `MTEXT`（段落以 `\P` 分隔）——DXF 的组码值不能跨行，
  把换行写进 `TEXT` 的值会产生 AutoCAD 拒绝打开的非法文件。
  由于可写版本都在 R13 之后，填充/样条/椭圆/构造线/射线一律按原生实体写出，
  不存在降级，导出也就不再需要降级告警。
  **文本编码按版本分档**：2000 ~ 2004 走代码页（简中 GBK，声明 `$DWGCODEPAGE=ANSI_936`），
  2007 及以后 DXF 一律 UTF-8、`$DWGCODEPAGE` 按惯例声明 `ANSI_1252`。
  这一档必须与版本号一致——声明 2007 却写 GBK 的文件，自己读自己时看不出问题
  （读侧跟着同一个声明走），别的 CAD 打开就是乱码。
  **`*ACTIVE` 视口按全图范围写出**：它决定 CAD 打开文件时的初始视图。省掉这一步，
  libdxfrw 会补上它自己的默认视口（中心 (0.65, -0.16)、视高 5.14）——一个贴着原点
  的极小窗口；图元只要不在原点附近，打开后就是一片空白。
  反过来，别人的文件能正常打开，也往往是它的 `*ACTIVE` 视图恰好覆盖了整张图。
  **文字样式随文件往返**：字体信息（`3` 主字体 / `4` 大字体，以及 AutoCAD 用来记录
  TrueType 字体的 ACAD 扩展数据 `1001/1000/1071`）由导入时收集进文档的文字样式表，
  导出时按原样写回，每个文字图元只写它的样式名（`7` 组码）——字体因此保持原样，
  不会在往返后被换成别的字体。文件没提供任何字体信息的样式（例如纯新建图纸）补上
  `txt + gbcbig.shx`：两者随 AutoCAD 分发，对全部可写版本都有效。
  少了这层兜底，CAD 会退回没有汉字字形的 `txt.shx`，汉字整片变成 `?`
  （MTEXT 走另一条取字路径，于是同一张图里往往「多行正常、单行全是问号」，极易被
  误判成编码问题）。
- `DwgCodec`：见第 5 节。

**render —— 渲染显示**

- `ViewTransform`：世界坐标（右手系，Y 轴向上）↔ 设备坐标（Y 轴向下）的换算。
  换算形式刻意只保留两个参数（原点的世界坐标、像素/单位），使所有视图操作都有闭式解，无需求逆矩阵。
- `EntityRenderer`：直线/圆/圆弧用**解析图元**直接绘制，不做折线近似，任意缩放下都精确；
  多段线的圆弧段按「像素矢高」自适应离散；屏幕半径超过 10⁵ 像素时曲率已低于一个像素，
  改用切线近似，既避免 Qt 光栅化定点坐标溢出，也省去无意义的海量分段。
  文字按像素字高旋转绘制（过小退化为占位点），含 `\n` 的多行文字整块参与对齐、逐行绘制；
  纵向对齐（DXF 73）按**字高框**（大写高度）换算而非字体行框的 ascent——用后者会把整块
  文字压低约 0.1~0.4 倍字高，与 AutoCAD/浩辰对不齐；
  选择框/包围盒与对齐方式一致（居中文字的框以锚点为中心，而非从锚点向右延伸）；
  填充以裁剪后的平行线族或实体填充呈现（过密退化轮廓）；
  标注绘制界线/尺寸线/实心箭头/居中测量文字。
  视口剔除对**零宽/零高的包围盒**（竖直线、点状图元）膨胀半像素余量再判——
  `QRectF::intersects` 把零宽高一律判为不相交，不补这一步竖直线会被整体剔除。
- `CadCanvas`：网格、坐标轴、图元、选中高亮、夹点、捕捉标记、十字光标。
  **它不理解任何命令语义**——所有语义由 `CanvasInputHandler` 的实现（`interact::ToolManager`）承担。
  这样换一套交互方案（脚本驱动、自动化测试、触屏手势）只需替换处理器。
- `PlotRenderer`：打印 / 打印预览的绘制核心。它不碰 `CadCanvas`、也不认识
  `QPrinter`，只接受「一个 QPainter + 一块目标矩形 + 每毫米多少设备像素」，
  于是打印、预览、导出 PDF、渲染成位图四条路共用同一份绘制代码，
  **预览即所得是结构上成立的**，不是靠两处代码写得一样来保证的。
  与屏幕渲染刻意不同的三点：纸面取景只有一种（出图范围铺满可打印区，底恒为白，
  没有栅格/坐标轴/选择高亮/夹点）；线宽按毫米落到设备分辨率上（屏幕上默认恒为
  1 像素，照搬会让粗细全丢——线宽参数在换算前还要先折算成「与纸面 1 mm 等长的
  世界长度」，否则粗线在放大的图上会错成一大片墨块）；出图范围与「缩放至图形范围」
  不同，**图层带「不打印」标志的图元不计入**，否则一张关掉的辅助图层会把主体压成
  纸上的一个小角落。

采用 QPainter 光栅后端而非 OpenGL：二维 CAD 的瓶颈在几何离散精度与图元数量，
而不在 GPU 填充率；光栅后端在远程桌面/虚拟机/无 GPU 环境下行为一致，对工程软件的可部署性更重要。
若需接入 GPU，只需替换 `EntityRenderer` 与画布的绘制循环。

**interact —— 用户交互**

- `SnapEngine`：对象捕捉（端点/交点/圆心/中点/象限点/垂足/切点/最近点/节点）+
  栅格吸附 + 正交 + 极轴追踪。捕捉带**优先级**：只要高优先级候选落在光圈内，
  更接近光标的低优先级候选也不会胜出——「端点」的工程意义远大于「最近点」。
- `ToolContext`：工具与文档/画布/捕捉/正交之间的唯一连接点，使工具构造函数保持单参数，
  新增交互选项无需改动任何工具。
- `Tool` / `ToolManager`：工具被建模为「由事件驱动的小型状态机」，命令行的提示文字就是当前状态的投影。
  **选择不是特例分支，而只是恰好作为兜底的那个工具**，消除了大量散布各处的 `if (无命令)` 判断。
- `CoordinateInput`：支持 `100,50` / `@50,0` / `50<45` 三种坐标形式，以及带括号的四则运算。
- 已实现命令：`LINE` `PLINE` `CIRCLE` `ARC` `ELLIPSE` `RECTANGLE` `POINT` `TEXT` `HATCH`
  `DIMALIGNED` `DIMLINEAR` `DIMRADIUS` `DIMDIAMETER`
  `MOVE` `COPY` `ROTATE` `SCALE` `MIRROR` `EXPLODE` `ERASE` `SELECT`。

**ui —— 界面装配**

`MainWindow` 的角色是**装配者而非实现者**：创建并连接文档、画布、工具管理器、功能区与各面板，
自身不持有任何几何或文件格式逻辑。图层面板与属性面板是纯视图——只发意图信号，
所有变更由主窗口落到 `Document` 的方法上，从而保证每次变更都进入撤销栈。

`PropertyPanel` 按**属性分组**组织，而不是把所有字段平铺成一张长表：
通用属性（图层/颜色/线宽/可见）对所有图元有效，`文字` 组只在选择集里有文字图元时出现，
几何信息是只读摘要。多选时每个字段各自求公共值——取值不一致的字段留空（显示「多种取值」），
**但留空不锁死**：水平对齐不一致不影响水平对齐之外的字段照常显示与修改，
为此 `Document::setEntitiesTextXxx` 四个入口互相独立，命令内部按「未赋值即不动」写回。

`RibbonBar` 是仿 AutoCAD 的**功能区**，与普通工具栏的区别在于「面板」这一层：
一组相关命令被包在一个带底部标题的方框里，面板之间用底色与描边隔开，按钮数量
上百时仍能靠分组找到东西。两种按钮形态分工明确——大按钮承载面板里的主要命令，
小按钮承载次要命令（每列三个紧凑排布）；面板还能直接嵌入下拉框，
因为「选当前图层」这类操作本质上就是一个下拉框而不是按钮。

**面板自成一块**：每个面板有自己的底色与描边（`ribbonPanelBackground` /
`ribbonPanelBorder`），面板之间不再画竖线——只靠一条 1px 竖线分隔时，按钮一多
就分不出「文件到哪结束、绘图从哪开始」。两套主题的取色方向相反且都是刻意的：
浅色下面板比功能区**更亮**（抬起），深色下面板比功能区**更暗**——按钮的悬停/按下
配色是照着功能区底色调的，深色下面板若做成更亮的一档，悬停色会贴得几乎看不出来。

**面板内容一律靠顶部排列**：大按钮、小按钮列、单独一个按钮或下拉框都贴着面板
顶边，多出来的高度全部落在下方。早期版本靠「列内上下各加一段弹性空白」给内容
定位，实际效果是垂直居中；而每个面板能分到的高度又不一样（面板里大按钮的个数
不同，`QSizePolicy::Expanding` 分走的高度就不同），于是同一条工具栏上
「撤销/重做」「矩形/点」「填充」各停在一个高度上，参差不齐。现在列的对齐方式换成
`Qt::AlignTop`（见 `RibbonPanel::startColumn`），小按钮与大按钮共用一条顶线。

**次要命令仍按分组竖排**：`addSeparator()` 结束当前列，因此一组小按钮就是一列，
超过三行才另起一列。列的高度就是内容高度，不需要「排满三行」——是否新起一列
取决于分组意图，而不是凑满行数。

每个面板里所有命令型按钮都汇到同一个信号并转给命令行执行，
因此**功能区只是命令行的图形外壳**，二者行为必然一致。

`Theme` 负责整套界面配色，走**调色板**而不是全局样式表：`QPalette` 是 Qt 原生机制，
Fusion 风格会据此绘制菜单、停靠面板、表格、滚动条、状态栏等全部标准控件——
一条 QSS 规则要照顾的控件，调色板一个角色就覆盖了。深色在界面上意味着十几个具体色值，
它们全部集中在 `Theme::Palette` 一处，功能区的样式表、图标换色、滚动容器底色都从这里取。

这里有一条踩过的坑值得记下：**不能在 `QApplication` 上设样式表**。样式表一旦设在应用级，
控件会改用 `QStyleSheetStyle`，此后新建的控件不再继承应用调色板——表现就是深色主题
「只生效一半」：窗口底色变了，下拉框、按钮却还是浅色，而且不报任何错。
Fusion 在深色下漏掉的唯一一处（拖动停靠面板的分隔条以 Window 色绘制，与背景几乎同色）
改用一层 `QProxyStyle` 补画，不引入样式表。

这条代理风格**只碰分隔条**。滚动条一度也被纳入其中，但那是走错了方向：Fusion 原生的
滚动条在深色下本来就清楚（滑块比底色亮三十多级），而且带两端箭头按钮；自绘既丢掉了箭头，
配色还要跟着多维护一份。**凡是调色板已经能表达的东西，就不要用代理风格重画**——
这与「不设应用级样式表」是同一条原则：先确认原生机制够不够用，再决定要不要接管。
功能区的横向滚动条现在也交回 Fusion 绘制，只在滚动容器的底色上做主题适配。

`IconLibrary` 是图标的唯一来源，从 qrc 读取 SVG 源码后按需栅格化。
不预先烘焙成 PNG 有两个原因：同一枚图标要在 16 / 24 两种尺寸下使用，
矢量源在每种尺寸下都清晰；资源体积也小得多。深色主题的实现方式是
**读取源码后整体替换调色板色值再重新栅格化**——Qt 的 SVG 渲染器不会按控件
调色板重新着色，所以图标源文件刻意只用一组固定色值，让这个替换保持简单可预期
（`tools/lycad_icon_sheet` 会把全部图标在两种主题、三种尺寸下渲染成一张总览图，
供人工核对，换错色值立刻可见）。

## 3. 功能一览

**绘图**：直线（连续绘制）、多段线（含圆弧段、**恒定/逐顶点宽度**——PCB 走线语义、闭合/放弃）、
圆（圆心半径/三点/两点/直径）、圆弧（三点/圆心起点终点）、**椭圆**（轴端点 / 中心点两种方式，
定轴方向时吸附到上下左右并给出追踪线与「水平 / 竖直」标记，定另一条半轴时标出该半轴及其端点）、
**构造线与射线**（定位点 + 通过点，构造线支持 H 水平 / V 垂直锁定方向，可连续绘制；
两图元共用一套工具状态机，命令 `XLINE / XL`、`RAY`）、
矩形、点、**文字**（字高/旋转/九种对齐组合）、
**填充**（ANSI31 图案/实体填充，边界取点闭合，支持凸度圆弧边界——「2 顶点 + 凸度 1」整圆焊盘）、
**尺寸标注**（对齐/线性/半径/直径，测量值实时推导，夹点拖拽重排几何）。

**编辑**：移动、复制（连续放置）、旋转、缩放、镜像、删除；夹点拖拽编辑；**双击文字编辑内容**（多行编辑框：回车确认、**Alt+Enter 换行**，进撤销栈）；**特性面板改文字属性**（字高 / 旋转 / 水平对齐 / 垂直对齐，选中文字时才出现）；窗选（自左向右）与交叉选（自右向左）。

**选择与捕捉**：单击拾取、Shift 增减、Ctrl+A 全选、对象捕捉（9 类）、栅格吸附、正交、极轴追踪。

**图层**：新建/删除/重命名、颜色、线型、线宽、开关/冻结/锁定；当前图层；锁定图层不可选择。

**视图**：滚轮缩放（以光标为锚点）、中键平移、缩放至范围/选择集、网格与坐标轴。

**界面**：仿 AutoCAD 的功能区，按面板分组组织全部命令（文件 / 绘图 / 修改 / 注释 / 图层 / 特性 / 视图 / 帮助），
大按钮 + 小按钮两种密度，图层面板与特性面板内嵌真实下拉框；38 枚自绘 SVG 图标。
**深色主题**：菜单栏、功能区、停靠面板、表格、命令行、状态栏与画布整体切换
（「视图 → 深色主题」或功能区上的「深色主题」按钮，两处状态同步）。

**命令行**：命令补全、历史回溯、坐标与算式输入、`Esc` 取消、空格重复上一命令、`F1` 命令列表。

**文件**：DXF 导入导出（可写目标版本 R2000 ~ 2018 六档；**R12 只读不写**）、**DWG 导入导出**（内置 libdxfrw / dwgW 原生，导入 R14 ~ 2018、导出 R2000）、拖放打开。
普通保存（Ctrl+S）用默认目标版本 **AC1032 (2018)**；**「另存为」的文件类型列表就是版本选择器**——
`AutoCAD 2000 DXF 文件` … `AutoCAD 2018 DXF 文件` 各一条（由旧到新排列，
默认选中 2018），末尾再跟一条 `AutoCAD 2000 DWG 文件`（DWG 写出版本固定 R2000，名字同样点明版本），
选哪条就等于选哪个目标格式与版本，不再需要单独的「DXF 目标版本」菜单项。
菜单里的**「导出」只导出 PDF**（一步到位；带纸张/比例/预览的 PDF 通路在「打印」对话框里）。

**打印**：打印（Ctrl+P）一屏完成——左侧设置（打印机或**导出为 PDF**、纸张 A0~A4/B 系列/
Letter 等、横向纵向、**出图比例**：适应图纸 / 1:1 / 自定义 1:n、份数），右侧实时打印预览；
出图范围铺满可打印区、白底、按毫米落线宽，纸面上只画图纸内容（无边框、无标题栏）；
固定比例下图纸超出一张纸时**自动分页**（先行后列，预览带页码栏可翻页）；
**「不打印」图层的图元不进纸面**；预览与打印共用同一份 `render/PlotRenderer`，
预览即所的是结构保证而不是巧合。
文字/填充/尺寸标注在导出时按规范写出（TEXT / MTEXT / HATCH / DIMENSION + 匿名几何块）。

能独立出错——中心错说明轴向取反；比值错说明长短轴挑错了那一条（用户先画的那条轴未必更长，
靠的是 `EllipseEntity::normalizeHalfAxes` 换主轴）；不闭合则说明另一条半轴长度没被换算进去。
另一半是**方向吸附的孔径行为**：偏 6 px 必须吸到「水平 / 竖直」，偏 200 px 不许吸（判据是
到正方向射线的像素垂距落在 12 px 光圈内），再加一条退化输入（轴的两个端点重合）必须被拦下
且不产生撤销记录。这一段的光标移动直接送进工具管理器、没走 `QTest::mouseMove`：离屏平台下
合成移动会被合并丢弃（实测三次里只有一次到达），而这里要验的是工具的吸附判定，不是事件投递。

「双击编辑」这一段同时验了三件事：内容修改进撤销栈、编辑框**打开时就看得到多行**、
**Alt+Enter 真的插入换行**。后两件必须一起验——断言里期望的内容带一个行内的换行，
用的是「追加后缀 → Alt+Enter → 再写一行 → 回车确认」，只要 Alt+Enter 退化回「确认」，
对话框就会提前关闭、期望值对不上。它优先挑文档里第一条**多行**文字来双击（没有才退回
第一条单行文字），因为在真实图纸里多行文字来自 MTEXT 降级导入，正是这条链路最容易出问题
的地方。编辑框本身也不用 `QInputDialog::getText`：那是单行输入框，多行内容打开后只看得见
第一行，回车又直接提交，用户补不出换行——详见 `ui/TextEditDialog.h`。

「特性面板文字组」那两行盯的是**面板到文档的那几根连线**：从面板控件反向驱动
（`setValue` / `setCurrentIndex`），要求字高、旋转、水平对齐、垂直对齐四项都落到文档、
各产生一条撤销记录，并把「选中非文字图元时整组隐藏」也一并验掉。目标值刻意取
「与当前值不同」的候选——这个工具要能跑在任意图纸上，而被选中的文字本来就可能是
90° 或居中，设成同一个值不会产生撤销记录，`+4` 的断言就会莫名其妙地失败。

「功能区顶线」那一项逐个面板比较**小按钮与大按钮的顶边坐标**，只要有一处相差
超过 3 px 就判失败。它盯的是「次要命令是否与大按钮同一条顶线」——这正是靠着肉眼
看很难说清楚、改起来却很容易再犯的一处：定位方式一旦换回弹性空白居中，某些面板
的列就会掉下去，而掉多少取决于该面板里有几个大按钮。

「面板分块」那一项更直接：把功能区渲染出来，取**面板内部**与**面板之间空隙**的
两个像素比灰度差，低于阈值就判失败——面板与功能区同色时，「哪里是一块」只剩面板
之间一条 1px 竖线。深浅两套主题各查一次，因为面板底色是两套主题分别取的，只查
浅色会让深色那一档悄悄退回同色。

其中调色板那一项是专门针对深色主题的抽查：它验证的不是「调色板设了没有」，
而是**调色板有没有真的落到一个位于停靠面板里的控件上**。挑下拉框而不是按钮，
是因为功能区里的下拉框有自己的样式表兜底，反而看不出应用调色板是否生效。

「小窗口」那一项则把窗口从 1500×950 缩到 1060×620 再抓一张：默认尺寸下内容刚好放得下，
滚动条根本不出现，而「深色底上的深色滑块」恰恰是深色主题最容易漏掉的一处。
该用例会数出实际可见的滚动条条数（当前 3 条：功能区横向 1、图层列表横向与纵向各 1），
条数为零即判定失败——那说明这条检查已经失效，而不是「没有问题」。

它逐个数过功能区上的每个按钮并检查图标是否为空——`IconLibrary` 对缺失的图标只会返回空
`QIcon` 并留一条警告，界面上表现为「按钮没有图案」，靠肉眼很容易漏掉。

文字选择框只罩住左下角、双击编辑被上层填充抢先拾取。

32 / 24 / 16 三种尺寸下渲染成一张总览图，供人工核对配色与各尺寸下的清晰度：

```bash
QT_QPA_PLATFORM=offscreen build/tools/lycad_icon_sheet icon_sheet.png
```

### 4.4 DWG 实样验证

DWG 解析的可用性无法用自造文件证明，因此拿本机安装的 AutoCAD 附带的
**720 个真实 DWG**（AutoCAD 2004 / 2007 / 2010 / 2013 各版本齐全）做了实测：

| 项目 | 结果 |
|---|---|
| 读取成功 | 671 / 720（93%） |
| 失败原因 | 均为 R12（AC1009）或更早——超出 libdxfrw 支持范围，且会明确报出识别到的版本号 |
| 角度单位定标 | 29018 个弧角度样本，用于确认「DWG 路径下是弧度」 |
| 抽样复核 | 60 个文件全部读取正常，几何合理（例如一个接地符号读出 1 弧 + 4 直线，弧包角 194.5°） |

这些文件是第三方图纸，**未收入仓库**，仅在本地用于验证。

同一张图纸的 DWG 与 DXF 还可以做**逐条对照**——这是发现「两条读取路径给出不同
结果」最直接的手段（第 8 节记录了一次 MTEXT 旋转丢失的缺陷就是这么定位的）：

```bash
LYCAD_DWG_SAMPLE=/path/a.dwg LYCAD_DXF_SAMPLE=/path/b.dxf \
    ./build/tests/test_libdxfrw dwgAndDxfAgree
```

不设 `LYCAD_DXF_SAMPLE` 时，取与 DWG 同名的 `.dxf` 作为对照；两个环境变量都没
设置时该测试自行跳过，不影响常规 `ctest`。

块参照同样可以拿真实图纸盯住——尤其要确认「导入后还是块参照」而不是被炸开：

```bash
LYCAD_BLOCK_SAMPLE=/path/属性块.dxf ./build/tests/test_block_insert realSampleIfProvided
```

同一张图的 DWG 与 DXF 还要读出**同一份块参照与属性**。DWG 的属性对象是独立对象，
字段序只能靠对照来定标，这条测试就是那把尺子（只给 DWG 时会自动找同名的 `.dxf`）：

```bash
LYCAD_BLOCK_DWG_SAMPLE=/path/a.dwg LYCAD_BLOCK_DXF_SAMPLE=/path/a.dxf \
    ./build/tests/test_block_insert dwgAndDxfAgreeOnBlocks
```

给新增的 DWG 实体定标时，`LYCAD_DWG_DEBUG=1` 会打开 libdxfrw 的逐字段调试输出
（DWG 的字段序无法从接口看出，只能靠它把「读到的值」和同一张图的 DXF 摆在一起看）。

**写出的 DWG 还要用另一套实现来验**：自己读自己写得对，不代表别的 CAD 也认。
[GNU LibreDWG](https://www.gnu.org/software/libredwg/) 是独立实现的 DWG 读写库，
把写出的文件交给它的 `dwg2dxf` 转一遍，再比对 INSERT / ATTRIB / SEQEND 与句柄归属，
能发现「自读自写正常、别的实现当成游离实体」这类问题——块属性的属主写错（应指向
INSERT 而非块记录）就是靠它发现的，症状是 `stale ATTRIB subentity` 警告加上属性
被导出两遍：

```bash
dwg2dxf -o /tmp/check.dxf /tmp/lycad_written.dwg   # 独立实现的解读结果
```

加上 `LYCAD_BLOCK_SNAPSHOT=<png>` 还能把样本离屏渲染成一张图片，人工看一眼
块参照到底画成了什么样（这条路径与命令行、出图共用同一个 `EntityRenderer`，
因此图片里能看到的东西就是用户能看到的东西）：

```bash
LYCAD_BLOCK_SAMPLE=/path/属性块.dxf LYCAD_BLOCK_SNAPSHOT=/tmp/blk.png \
    ./build/tests/test_block_insert
```

## 5. DWG 支持

### 导入：内置 libdxfrw 原生解析

`third-party/libdxfrw-modify`（基于 libdxfrw 0.6.3）随项目一起编译，
DWG 与 DXF 的解析都在进程内完成：

- **支持 R14 ~ 2018**（AC1012 ~ AC1032）
- 不依赖任何外部程序，不产生中间文件
- 内置解析失败时（例如文件是 R12、或内容损坏）如实上报失败原因，
  不做静默降级，也不会用一份内容不完整的文档冒充成功

适配层在 `io/LibDxfRwAdapter.cpp`。libdxfrw-modify 的头文件只在该文件中出现，
不外溢到项目其它部分，因此将来更换或升级解析实现时改动面被限制在一个文件内。

### 关于角度单位（这里是实测定标的结果）

libdxfrw 在「读 DXF」与「读 DWG」两条路径下，对同一字段的单位处理**并不一致**。
这一点无法从它的接口看出，只能逐个字段核对源码并实测确认：

| 字段 | DXF 路径 | DWG 路径 | 适配器的处理 |
|---|---|---|---|
| 圆弧起止角 | 弧度 | 弧度 | 直接用 |
| INSERT 旋转 | 弧度 | 弧度 | 直接用 |
| **TEXT 旋转** | **度** | **弧度** | **按来源分别换算** |
| MTEXT 旋转 | 取自 11 组码方向向量 | 同左 | 由方向向量算 `atan2`，不看 50 组码 |
| 标注角度 | 度 | 度 | 转为弧度 |

实测依据是 720 个真实 DWG、共 29018 个弧角度样本：出现次数最多的取值依次是
`3.141593`(π) ×1234、`4.712389`(3π/2) ×1069、`1.570796`(π/2) ×1003，
而「接近整数度」的样本数为 **0**。文字旋转在 DWG 中恰为 π/2、在 DXF 中则是 90.0。
适配器据此按来源分支——删掉这一处会让 DWG 里的 TEXT 旋转整体错 57 倍，
而 DXF 一切正常，这类缺陷在使用中极难归因。

MTEXT 走的是另一条路：它的旋转不写在 50 组码里，而是 11 组码的「X 轴方向向量」，
所以两条路径都按方向向量算 `atan2`，不存在单位之争。但方向和单位一样容易漏——
DWG 路径需要 libdxfrw 明确标记「11 组码是方向向量」，漏标就只能退回永远是 0 的
`angle`。这个缺陷在 libdxfrw-modify 里已修正，另有 DWG/DXF 实样对照测试盯着
（见第 8 节）。

### 文本编码：两套存放方式，各管一个年代

DWG 里的文字有两种存放方式，与版本相关，读错就是满屏乱码：

| 版本 | 文字的存放 | 读出依据 |
|---|---|---|
| R12 ~ 2004（AC1009 ~ AC1018） | 单/双字节代码页（简中为 GBK） | 文件头 `$DWGCODEPAGE`，走内置代码页表 |
| 2007 及以后（AC1021 ~ AC1032） | UTF-16 | 无需查表，直接转 UTF-8 |

这条规则本身很简单，麻烦在于上游**选择解码器的那处逻辑带了一个进程级的状态**：
同一个进程里先打开一个老版本文件，后面打开的 2007+ 文件就会被按老代码页去解，
中文全成乱码。720 个真实 DWG 中，173 个 2007+ 文件里有 59 个会被这个状态带偏；
libdxfrw-modify 已改为只看当前文件的版本，并有回归测试盯着（见第 8 节）。

### 导出：内置 dwgW 原生写出（R2000）

libdxfrw 上游只读不写；本项目为它补齐了 **AC1015（AutoCAD 2000/R2000）的原生写出器**
（`intern/dwgwriter15.cpp`，对外接口 `dwgW`，与 dxfRW 的写出侧同构）。因此 DWG 导出
在进程内完成，不依赖任何外部程序：

- 目标版本固定 AC1015：兼容面最广，AutoCAD 2000 及以上的版本都能直接打开
- 写出失败时如实转述原生写出器的错误，不静默降级
- 这条链路有测试覆盖：`test_libdxfrw` 的**原生写-读往返**测试盯住坐标编码——
  DD（带默认值的压缩 double）的分支语义必须与读取端严格对偶，否则坐标
  会悄悄退化成垃圾值（实测曾让几乎所有直线读回时长度只剩 1e-5）；
  `test_dwg_codec` 则盯住编解码器这一层：写出的是二进制 DWG 而非 DXF 副本、
  失败时文档不留半成品

### 一道廉价的内容预检

DWG 是二进制格式，而有些文件会把 DXF 内容套上 DWG 签名——被误改扩展名的 DXF、
损坏后剩下的文本残件都属此类。这类文件交给解析器会让它长时间空转：
实测一份伪装文件耗掉 **108 秒**，界面会整个卡住。现在读取前先做一次 512 字节的
可打印字符统计，把这类文件挡在解析之外（实测降到 **99 毫秒**），真 DWG 不受影响。
60 个真实 DWG 样本在该检查下全部照常读取。

## 6. 已知限制

| 限制 | 说明 |
|---|---|
| 圆/圆弧在非等比缩放下被近似 | 椭圆已是**独立的图元类型**（ELLIPSE 的读写、绘制、捕捉、属性面板都支持），但圆的变换仍按等效均匀缩放处理，不会自动转成椭圆。等比缩放与镜像下为精确结果。 |
| 出图固定比例超出纸面即分页 | 适应图纸恒为一页；固定比例（1:1 / 自定义）下图纸超出可打印区时按先行后列自动分页，预览与打印页数一致。不做「缩到一页」与拼页顺序之外的打印样式（页边裁切线、页码标注等）。 |
| 块参照的几何不可直接编辑 | 支持块定义 + `INSERT` 的完整往返、显示、拾取、捕捉、属性面板与 分解(EXPLODE)。但**没有块编辑器**（不能双击进块改内容），也没有 `BLOCK`/`INSERT`/`WBLOCK` 命令（不能新建块或再插入），`MINSERT` 的阵列在变换后会被烘焙展开。要改块内容先 `EXPLODE` 打散；非等比拉伸落到块参照上时几何同样被烘焙进一份匿名块定义副本，该处不再是引用（几何精确）。 |
| 未实现逆向编辑 | 不支持 OFFSET / TRIM / EXTEND / FILLET / CHAMFER / STRETCH。刻意保留为未实现状态而非半成品。 |
| 未建模的实体类型 | 多行文字（MTEXT）、角度标注、公差与引线标注。导入时按类型计数跳过并明确告知，不静默丢弃。 |
| 文字为 TEXT 模型（内容可含换行） | 对应 DXF `TEXT`：支持镜像生成标志（71 bit2/bit4，PCB 背面丝印即此表达）与宽度因子（41，含负值=镜像）。内容里的换行会被保留：画布按多行绘制、双击弹出的编辑框按多行打开（Enter 确认 / Alt+Enter 换行）、导出到 R2000 及以上时写回为 MTEXT。**MTEXT 实体本身仍未建模**：导入时降级为多行文字并计数上报，其内联格式码只还原字体与段落对齐两项，其余（行距、栏宽、制表位等）不保留。文字样式（`STYLE` 表）已随文件往返：图元带样式名（7），字体（3/4 组码与记录 TrueType 字体的 ACAD 扩展数据）存在文档的文字样式表里按名解析，导出原样写回；只有界面上的样式管理（新建/改名/删除）尚未提供。 |
| 标注样式固定 | 测量文字字高固定 3.5（读入时不解析 DIMSTYLE），无标注样式管理器；箭头/文字位置由定义点推导，不支持用户自定义箭头形态。 |
| 填充为单环边界 | 支持直线与凸度圆弧混合的单个外部环（含「2 顶点 + 凸度 1」整圆焊盘）；多环嵌套与样条边界取第一个可解析环。 |
| EDA 图层配色为启发式 | 文件自带颜色时严格按文件显示；仅当 EDA 导出的 DXF 缺失图层颜色时，才按图层名关键词套用行业惯例配色（顶/底丝印分色：顶黄/底绿，与常见 EDA 2D 视图一致），可在图层面板修改，导出时随图层表写出。 |
| 线型为内置标准集 | 支持 CONTINUOUS / DASHED / DASHDOT / DASHDOTDOT / DOT / HIDDEN / CENTER / PHANTOM / BORDER；文件中引用的自定义线型会回退为 CONTINUOUS。 |
| 单图纸空间 | 无布局/视口体系，仅在模型空间工作；图纸空间里的实体也会被一并导入到模型空间。 |
| 不支持对象编组 | 未建模；文件里的 `GROUP` 对象在读取时按对象跳过。 |
| 功能区宽度靠滚动而非折叠 | 面板排开的总宽度大于窗口，窗口偏窄时出现横向滚动条。AutoCAD 的做法是把放不下的面板折叠成一个按钮，本项目未实现该机制——滚动不会隐藏任何功能，只是需要多一次拖动。 |
| 图标为自绘，非 AutoCAD 原图标 | 形态按 AutoCAD 的表达习惯绘制（夹点、箭头、虚线辅助线），但不复制其美术资源。 |

### 对上游源码的修改（libdxfrw-modify）

全部集中在下表这些位置，均带有说明注释，并有回归测试：

| 位置 | 修改 | 原因 |
|---|---|---|
| `intern/drw_textcodec.cpp` | 解码器只看当前文件的版本 | 上游用函数内 `static` 记录「进程见过的最低版本」来选解码器：先读老版本文件，之后 2007+ 文件的文本全被按老代码页解码。实测 173 个 2007+ DWG 中 59 个中招，汉字总数 156 → 20 |
| `drw_entities.cpp` | DXF 的 60 组码按规范取反；DWG 的 invisibleFlag 赋给 visible | 上游 DXF 路径把 60=1（不可见）当 visible 用、DWG 路径读出标志后丢弃，隐藏图元一律被读成可见 |
| `intern/dxfreader.cpp` | 二进制 DXF 组码按规范 1 字节读取（255 为转义符） | 上游按 2 字节读组码，任何合法二进制 DXF 都解析失败（最小样例读出 0 个图元） |
| `intern/drw_textcodec.cpp` | 双字节代码页（936/949/950/932）改为直接在码表上二分查找，不再按引导字节表划区间 | 引导字节表（`DRW_LeadTable*`）是手工维护的前缀和，与码表对不上：实测 936 有 3 处、932 有 29 处、949/950 各有几处错位。整段码位因此被划到邻居名下：落在缝里的字查不到，退化成 `?`（实测某张中文图纸里有 20 个字中招，如「个」「更」「各」；解码按完整码位比对，因此只会变 `?`、不会误命中别的字）。四张码表本身按码位严格升序且无重复，二分查找既准确又不依赖那份表 |
| `drw_interface.h` / `libdxfrw.cpp` | 新增 `addUnknownEntity` 回调 | 上游对不认识的实体类型（MLINE、MESH 等）静默跳过，应用层无从计数上报 |
